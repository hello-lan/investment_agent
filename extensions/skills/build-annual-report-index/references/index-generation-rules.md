# Index generation rules

当某份年报还没有章节索引时，先按本规则生成 **chapter index JSON**，再进入后续阅读流程。

## Goal
索引的目标不再是输出少量平面 `sections`，而是生成一份**最多两级的章节树**，帮助后续：
- 先按目录理解整份年报结构
- 直接按行号回查关键章节
- 在不同公司、不同年份标题略有差异时，仍然尽量使用报告里的真实标题

## Output shape
输出采用统一的 chapter 树结构：

```json
{
  "report_file": "reports/company-a/annual-report-2024.md",
  "company": "<company>",
  "ticker": "<ticker>",
  "year": 2024,
  "index_version": 2,
  "chapters": []
}
```

每个节点至少包含：
- `chapter_id`
- `title`
- `line_start`
- `line_end`
- `priority`
- `reason`
- 可选 `children`

## Core rule
索引以**行号为主、标题为辅**：
- `line_start` / `line_end` 用于后续直接读取
- `title` 使用报告里实际命中的标题，不轻易改写
- `chapter_id` 提供稳定标识

## Top-level chapter rule
### 普通顶层章节
第一步读取目录后：
- 除最后一个 `财务报告` / `财务会计报告` 外，其余顶层章节都进入顶层 `chapters`
- 名称优先以目录中识别到的**实际标题**为准
- 再按原流程去正文定位真实 `line_start`

### 财务报告特殊处理
最后一个 `财务报告` 不保留为父节点，而是只索引其下一层关键条目，并把它们提升到顶层：
- `财务报告-审计报告`
- `财务报告-合并资产负债表`
- `财务报告-合并现金流量表`
- `财务报告-合并利润表`
- `财务报告-重要会计政策及会计估计`
- `财务报告-合并报表附注`

其中：
- 输出名称统一带 `财务报告-` 前缀
- 但前缀后的标题部分应尽量保留原文实际命中名称
- 只有 `财务报告-合并报表附注` 允许再展开一层 `children`

## Second-level rule
### 需要展开一层 children 的普通章节
只对以下两个顶层章节建立一层二级索引：
- `公司简介和主要财务指标`
- `管理层讨论与分析`

### 二级标题来源
这些二级标题通常不在目录中完整列出，因此不要依赖目录：
1. 先定位父章节边界
2. 仅在父章节范围内做有界扫描
3. 提取形如 `一、`、`二、`、`三、` 的一层小节标题
4. 标题以原文实际命中名称为准

### 附注 children 规则
对 `财务报告-合并报表附注`：
- 只索引一层主条目，例如 `1、货币资金`、`2、交易性金融资产`
- 不继续递归到 `（1）`、`（2）`
- 不把表格行、页码、页眉页脚当成附注科目条目
- 科目名称以报告原文识别到的实际名称为准，不预设固定清单

## How to locate titles
### 顶层章节
1. 先增量读取文件开头，抽出目录
2. 用目录里的标题作为 strongest alias
3. 搜索正文候选行号
4. 命中多个候选时，读取前后窗口确认真实标题
5. 用下一个已确认顶层节点的 `line_start - 1` 作为当前节点 `line_end`

### 二级标题
1. 先定位父章节边界
2. 在父章节内逐行扫描，识别看起来像一层小节标题的行
3. 对跨行或断裂标题，允许拼接 2-3 行窗口后再判断
4. 只在扫描法明显不稳定时，才退回“读取整个父章节后一次性提取”的兜底策略

### 财务报告条目
1. 先定位 `财务报告` 根章节，但不输出它
2. 把它仅作为有界搜索窗口的开始
3. 在该窗口内搜索指定的关键条目
4. 对命中的真实标题统一加 `财务报告-` 前缀输出

## How to set line ranges
1. 用真实标题所在行作为 `line_start`
2. 同层下一个已识别标题的前一行作为 `line_end`
3. 若是同层最后一个节点，则以其实际结束处为准
4. 不要让同层节点重叠
5. 不要为了“保险”把大段无关内容并入区间
6. 二级节点必须完全落在父节点区间内

## Priority assignment
可按以下默认规则标注优先级：
- `管理层讨论与分析`、财务报告关键条目：`P0`
- `公司简介和主要财务指标`、`股份变动及股东情况`、`债券相关情况`：`P1`
- `公司治理`、`环境和社会责任`、`释义` 等：`P2`

如果实际标题显示更高信息密度，也可以适度上调，但不要因为保守而全部标成 `P0`。

## Reason writing rules
`reason` 要解释“为什么读它”，不要只是复述标题。

好例子：
- `用于快速建立公司基础信息和核心财务指标的整体认知`
- `用于确认关键会计政策、估计口径和潜在口径变动`
- `合并报表附注中的一层科目“货币资金”，便于按科目定向回查`

差例子：
- `这是重要章节`
- `需要阅读`

## Quality checks
生成后至少检查：
- 顶层 `chapters` 是否按 `line_start` 单调递增
- 是否错误保留了原始 `财务报告` 父节点
- `公司简介和主要财务指标`、`管理层讨论与分析` 是否有一层 `children`
- `财务报告-合并报表附注` 是否有一层 `children`
- 是否出现第三层结构
- 标题所在行是否与输出标题一致或高度对应
- `line_start <= line_end`
- 子节点是否完全落在父节点区间内

## Guardrails
- 不要默认读取整份年报
- 不要把目录命中直接当成正文 `line_start`
- 不要为财务报告保留原始父节点
- 不要预设附注科目固定名称清单
- 不要把表格行、页码、页眉页脚识别成标题
- 不要继续展开第三层结构
